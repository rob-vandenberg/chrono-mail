# DECISIONS.md

The design rules as they stand now, by topic, one short entry each. Every number D-001 to D-283 is here (code and tests cite them; D-030 and D-042 are split over two topics). How a rule is built, measurements, the story behind it and the full old wording are in `DECISIONS-ARCHIVE.md` (git-ignored; search by number, never read whole: the last match is the newest wording) and in `DEVLOG.md`.

**Maintaining this file (D-162):** a new decision goes into its topic with the next number (next: **D-284**): the rule in one to three sentences, `Why:` in one line, `Rejected:` only when someone might propose it again. No function names, measurements, screen layouts or history: those go to DEVLOG.md. An entry stays under about 600 characters. When a decision changes, copy its old wording to the end of the archive first, then rewrite it here. A decision that no longer holds becomes "→ D-nnn".

## 0. The basic rule (read first; it comes before every other decision)

- **D-193** (the owner) **An account is a faithful copy of the account on its server** (IMAP, CalDAV, CardDAV). The full rule is AGENTS.md §0: server first, here only when it confirms; every server change shows at the next sync; offline done here, remembered, sent later; a lasting refusal is a sync conflict, a passing failure is retried; two computers end up the same; exceptions: local data, POP3, and local-only data the owner approved (D-172, D-191, D-201). Every changelist says how it keeps the rule; every fix is tested online, offline and back, refused, changed on the server, two computers.
- **D-201** (the owner) **What the server supports is synced; what it does not support stays on this computer only**, with no extra folders or hidden records on the server. So far local only: snooze times, archive origin, tag colours and shortcuts, tags on a server without keywords (Kerio), the calendar palette, Scheduled messages. Given once for all: never asked per feature.

## 3. Storage, index, keys (never lose mail)

- **D-004** Messages are an encrypted Maildir: one file per message, authenticated encryption, random names with the flag suffix (a flag change is an atomic rename). Rejected: SQLite as the store, PST, zip, mbox.
- **D-005** The index is SQLite, never the truth, rebuildable at any time, not encrypted.
- **D-006** The model is IMAP-shaped; POP3 is a restricted account on top.
- **D-021** Five flags (D F R S T). A folder path is a tuple of names; `MessageRef` = (account, folder path, store id). Unknown Maildir letters are kept. The model holds no passwords.
- **D-022** `parse_message` never raises (a failure is a defect string). Caps in `mime/limits.py` (depth 20, 1,000 parts, header 1 MiB, part 256 MiB, 50 defects). A date without zone is UTC. Non-ASCII addresses are refused (no SMTPUTF8).
- **D-023** AES-256-GCM, a key per file by HKDF-SHA256. The data key is in the OS credential store (`keyring`). Backup: a recovery file (scrypt, capped parameters) and a 58-character recovery code. Not built: master password, key change. Rejected: Argon2, a key in a plain file.
- **D-024** Store layout: separator `!` everywhere; folders `f-<12 hex>` with `folder.json`; a delete moves to `.deleted/`, purging is explicit. Delivery: tmp, fsync, rename, fsync the directory, then verify (read back, decrypt, compare); a failed verify removes the copy and raises. Switching encryption is not built.
- **D-025** One SQLite index per account, WAL, FTS5 contentless (SQLite ≥ 3.43); body text capped at 100,000 characters; search terms always quoted (no FTS injection). A rebuild writes a new file and renames it in. An unreadable message shows as "(damaged message)".
- **D-031** Index formats 2 to 13 (13: the paperclip by D-235; 12: the Sent moment, D-228; 12 and 11 are upgraded in place and filled in afterwards, D-229; older ones are rebuilt). The engine keeps the data key for the session; SQLite waits up to 30 s for another writer.
- **D-229** (the owner) **Index rebuilds at start**: every index is checked before the mail is shown; unusable ones are rebuilt one after the other in a window with progress (Account n of m, how many of how many); the mail checks wait meanwhile. An index of format 11 or 12 is upgraded in place: usable at once, what it lacks filled in afterwards in the background. Run in background only while the old index stays usable, and a click on the busy bar in the status line brings the window back; Abort asks first and closes the program only when nothing usable is left. The mail is never touched; the old index stays in use until the new one replaces it.
- **D-026** Settings are one JSON file (atomic, owner-only); data in the platform data directory; unknown keys ignored, a damaged file copied to `.bad`. Account ids are validated 128-bit hex. Passwords only in the credential store. POP3 default: keep on server.
- **D-170** (R-20) The key check tells "the key is missing" apart from "the wallet could not be asked", each with the store's own reason. Why: one guessing text hid the cause.
- **D-176** **A message has at most two files: itself and, only when needed, its properties file** (`properties/<store id>.json`: tags, snooze time and origin, archive origin). Our own waiting messages carry their schedule in themselves (headers); recording progress replaces the message under the same id, verified first. Written atomically per message; a damaged file fails only that message. Why: data saved beside the acting account went missing for other accounts. Rejected: one properties file per mailbox; a file next to the message.
- **D-136** Every read and save of `config.json` holds one engine lock (`Engine.change_config`); long work outside it.
- **D-220** (R-16) Code two lower layers both need exists once, in the lowest layer both may reach (credential store door in `core`, index opening in `index/database.py`, the line connection in `protocols`). Rejected: a new shared layer.
- **D-127** Every credential-store failure is a normal error with its reason; no automatic retry (it would hide the fault). Every call waits at most 60 s, then a clear error. Rejected: a time limit in every window's wait.
- **D-260** (batch 5, RV-03) **A new data key's recovery code is shown until the person confirmed it is stored** (Done with the tick), remembered through a restart: before every restore and after an account is added; a restore goes on only after it. While an account is being added its window cannot close. Keys made before 3.5.346 count as stored. Also (batch 5, RV-77): a drag of messages of several accounts goes to no folder, as Move to offers none; nothing moves halfway without a word. Why: a restore stopped at the code, or Cancel during Add account, made the key and never showed its code again. A recovery code that could not be shown can be asked again with Try again.
- **D-035** A missing key at start opens a dialog: recovery code, recovery file, or try again; "Not now" leaves a red status line.
- **D-043** Export writes the .eml as received (atomic, 0600, unencrypted); source view capped at 2,000,000 characters; printing never uses the mail's HTML.
- **D-235** (the owner) **A part is left out of the attachments only when the text shows it** (the HTML text refers to it by cid:), whatever the sender labelled it; everything that asks "has attachments" follows. Attached pictures the text does not show are shown below it, fitted to the width, never enlarged, and stay attachments too (B-11). Why: a picture labelled inline in a plain-text message was shown nowhere.
- **D-236** (the owner) **A file of the message works as in a file manager**: a click selects it, a double click opens it, a right-click on it or on a picture of the message offers Open attachment and Save as…. Open writes a copy, readable by the person only, to Chrono Mail's own folder (emptied at the next start) and hands it to the program for its kind of file; **a file that runs when opened is asked about first**. Why: a click saved at once; one click must never run a stranger's program.
- **D-100** Folders are made under a lock per store (`ensure_folder` everywhere); twins are merged when the store opens. Not covered: the program and the CLI at the same moment. Cancel snooze: back to the origin folder, else the Inbox, unread.
- **D-107** Every index change starts with `BEGIN IMMEDIATE`. A missing message file is `MessageNotFoundError`.
- **D-108** Maintenance runs once per place where mail is kept; its report can be copied.
- **D-109** A message whose file is gone: delete-type actions remove it from the index; other actions show the error; one warning per action. The index is never repaired by itself (Settings > Repair the search index).
- **D-115** → D-145.
- **D-145** The index lock is `engine/session.py` `index_lock`; one rebuild at a time.
- **D-248** (W13) **Nothing looks through a folder for a message whose place is known**: storing, copying or moving a message gives back where its file is now, and the index takes that place. Why: each delete read every file name in Trash again, so a large delete slowed down as Trash filled.
- **D-247** An index file is made or upgraded only after its format is read again under the write lock; a current file is opened without the lock. Why: two parts opening a new calendar index at once took it for damaged and removed it while the other used it.
- **D-251** (RV-62) **Local Folders whose mail is on this computer is never made again or removed**: missing from the settings (settings lost or reset), it is taken back as it is, with the key it was written with; a first setup that fails removes only what it made itself. Why: the setup erased the kept mail and the calendars of this computer.
- **D-265** (the owner's question of 2026-10-25) **Local Folders kept here is never cut off by a new key**: no new key is made while it needs its own; written with an older key this computer still has, it is taken back and written again with this computer's key (the old files kept aside); when that key is gone for good, Start without this mail sets it aside, never deleted. A restore takes it back first and adds to it. Why: adding an account first made a new key, and that mail could never be opened again.
- **D-255** (the owner) **Local Folders can never be removed, only hidden** (Settings > Sidebar). Why: it holds the mail, calendars, contacts and tasks of this computer.
- **D-125** Bulk import syncs once per batch, then writes the journal. A duplicate counts only when its index copy decrypts. Rejected: writing without any sync.
- **D-244** (B-22, the owner) **Backup and Restore are Chrono Mail's own .cmz file** (Import and Export are for other programs). A .cmz is a ZIP of the chosen parts of the chosen accounts exactly as kept here, decrypted, each account with its definition and identity; passwords only in a protected backup; protection is standard ZIP AES-256 with a 24-letter-and-digit password the program makes. A backup only reads. A restore asks this computer's key first (its recovery code in its own window), then the file, then its password; an account not here comes back whole under its own identity, one that is here gets only what it lacks (never what its server holds), and the server still wins (D-193); Remove all data first sets this computer's data aside until the restore succeeded. The person ticks which parts and accounts of the backup come back (as in Backup); a ticked account always brings its definition. Why: a backup must survive the loss of this computer and its key. Rejected: a password the person chooses; Chrono Mail's own encryption (the file should open with 7-Zip too). A damaged message or item of a backup is left out and told, the rest comes back; the data set aside is then kept. An account without files comes back too. Only the rules of the accounts that come back. The first-account window offers Restore a backup…. **(the owner, 2026-10-26) After a restore everything is back exactly as the backup holds it**; the only exceptions are D-245's (nothing is sent by itself) and Local Folders kept here, which is taken back first as at every start (D-251, D-265). A scheduled message comes back scheduled; an account the settings lost whose files are still here comes back as the backup holds it, its older files kept beside it and named in the report. Rejected: pausing every scheduled message; taking such an account back and adding to it (it could send its old Outbox).
- **D-261** (the re-check of the review, RV-193 to RV-199) **A restore never touches more than it set aside, and names only what came back**: when setting this computer's data aside stops half-way, nothing is moved or removed; a restored IMAP account's list of the server's messages names only the messages that came back (the others are downloaded again, never deleted on the server), a folder that did not come back is synchronised afresh with the person's choices for it kept, deletes made offline stay; an older backup (before 3.3.343) of a POP3 account that deletes on the server what it lacks names only messages that are here. An older program reads the restored folder as deleted here (it hides it; nothing is deleted). Why: a failed restore could delete all mail, and a restore could have mail deleted on the server.
- **D-252** (RV-60) **A restore waits for the work that talks to the servers** (checks, sends, calendar syncs) to end and holds new work back until it is done. Why: Remove all data first set the mail aside while a POP3 check still deleted it on the server.
- **D-253** (RV-59) **A restore writes nothing outside the account's own folder**: a name in a backup with "..", a drive or a backslash is left out and told as damaged. Why: a crafted backup could write files anywhere the person may write.

## 5. POP3, SMTP, sending

- **D-027** Own POP3 client with caps (line 1 MiB, message 256 MiB, 1,000,000 messages, timeouts); STLS never skipped. Order: retrieve, store and verify, log with fsync, only then DELE (committed by QUIT). Deletion is blocked when the store looks damaged or empty, or more than half of at least 10 are missing.
- **D-036** "Leave all mail on the server" is the default.
- **D-028** SMTP on `smtplib` with a capped reply reader; STARTTLS never falls back. Order: build, store a verified Outbox copy, send, move to Sent. A failure stays in the Outbox and is tried again at every refresh that sends (the owner, 2.2.314).
- **D-088** Our Outbox and Sent copies keep Bcc; it is stripped just before SMTP. Refresh = Send and Receive All, with a menu. Forward as attachment attaches the original unchanged.
- **D-037** A draft is a message in Drafts. Saving stores the new version before removing the old; autosave every 30 s; the window stops autosaving the moment the engine has the message. A failed autosave shows in red on the window's bottom line, never in a box (a failed Save asked for also shows the box).
- **D-271** (CR-03) **While a draft is saved, the person's newest decision waits and is done once the save ended**: Send, Save on close and Discard replace the one waiting, a plain Save waits only when nothing else does; Discard of a draft the window made hides it at once and deletes that draft after the save; quitting lets this end first. After a save only the attachments it took are marked as stored, at the places the save gives. Why: a file attached, Send or Discard during a save was lost, undone or left a draft.
- **D-272** (the owner) **Messages move to a folder of another account message by message**: each is read with its marks and tags, stored in the other account under its own id and read back (an IMAP target on the server first; offline stored here and put there at the next check), and only then removed from its own account for good (an IMAP source on the server first; offline at the next check). Stopped at any moment, a message is in one account or both, never in neither; done again, nothing is stored twice. Groups of 50; the two accounts are never open at once. The junk filter learns as for a move within an account; snooze time and archive origin stay behind (they name the old account's folders). A refused upload leaves the message where it was and says why; refused later after an offline move it is a sync conflict (D-195). Undo moves back, Redo again. Move to has a submenu per other account; the folder list takes a drop on another account's folder (not Outbox or Scheduled; a scheduled message stays in its account); a drag of messages of several accounts (Favorites) names each message's account and goes to one folder (3.6.367). Why: the owner. Rejected: a temporary folder on the server with one move at the end (other computers would see it, a crash leaves it behind, and a half-done move is a correct state); overlapping uploads (about 10 ms per message on both test servers, measured).
- **D-246** (the Windows computer's wording notes) **A count is written one way**: "1 message", "2 messages", "1,041 messages", never "message(s)" (one helper in `core`). Numbers stay in the English form until B-04-1.
- **D-245** (the Windows computer's W6, the owner) **Nothing is sent that the person did not send, schedule or let a refresh send.** The check after a restore, an index rebuild, an import or a new account only receives; a refresh a rebuild held back runs after it with its own choice. A restore brings the Outbox's mail back in Drafts and pauses a scheduled message whose time passed (one-off and repeating; one-off ones can be paused and resumed too). Why: a restore of an old backup sent its old Outbox. Rejected: keeping restored mail in the Outbox (any refresh sends it).
- **D-258** (batch 3, RV-61) **What a POP3 account downloaded never names a message a restore did not bring back.** The backup takes the download list before it lists the mail; a restore leaves out of it the messages that were damaged, and, for an account that keeps its mail in Local Folders while that mail does not come back with it, every message not in Local Folders here. A message left out is downloaded again: twice at worst, never deleted on the server. Also: a damaged part of a backup (a description, a message's details, a setting, an oversized file) is left out and told, the rest comes back; Replace keeps where an account's mail is kept and its encryption. Why: a named message that is not here is deleted on the server by "delete from the server when deleted here". A damaged record of the server in a backup leaves out only that account's messages or items (the server keeps them); a damaged POP3 list only itself; any other file an account cannot come back without only that account; this computer's damaged tags file is kept as .bad, as its rules file.
- **D-262** (the re-check of the review, RV-178 to RV-184) **The send locks come in one order, the mailbox first**: open the mailbox, then the repeat lock, then the Outbox lock; Unschedule does all its work under them (it may wait for a running check, never send twice). A message the server took (marked as sent) is filed in Sent without a countdown or password, never moves or is copied anywhere but Sent or Trash, never becomes a draft. A scheduled message is sent only when it was still in Scheduled at that moment; one deleted or moved away meanwhile is not. Removing a message of the Outbox or Scheduled never needs the IMAP server. Why: each of these sent a message twice, sent one that was withdrawn, or froze the program. A message the server took moves only to Sent, Trash or back to the Outbox; one in Sent never moves into the Outbox or Scheduled; a message leaves Sent only without left-over sent marks (cleared first, else it stays). The group step on an IMAP server leaves out what each message's own step refuses.
- **D-264** (the owner's question of 2026-10-25) **That the server took a message is kept three ways**: a letter in its file name (a rename, so a full disk cannot stop it), the time in its properties file, and this run's memory; any one means never sent again and never a draft. Why: on a full disk the mark could not be written and the next refresh sent it again.
- **D-256** (RV-109 and the rest of batch 1) **A message in the Outbox is sent by one path only, once**: every send holds the Outbox lock from storing its copy until the server answered; a message the server took is never sent again, also when its move to Sent failed (marked as sent) or the server dropped the goodbye; a failed repeating try leaves no copy; a message opened to be changed leaves the Outbox first. Why: five ways sent the same mail twice. Once the server took a message, nothing after it (telling the list, the Sent copy on the server) makes it a failed send: a failure there is a warning (3.6.351). A send that failed after its copy may be stored says to look in the Outbox and Sent, never "nothing was stored".
- **D-241** (B-21, B-20, the owner) **Delaying a send**, two independent ticks in Settings > General: a delay of N seconds (the message waits in the Outbox with a "not before" time in its properties file, a notice at the bottom left offers Send now and Cancel; Cancel opens it again as a message not saved yet), and "until the next refresh". Every send of the Outbox keeps the "not before" time; one message at a time is sent, never twice. Quitting with mail in the Outbox asks first, with Do not warn again.
- **D-055** Send later keeps the message in Scheduled (D-172); at its time it is rebuilt, a verified copy stored, the original removed, then sent. Snooze writes the record in the properties file before the move to Snoozed. The program must be running.
- **D-169** (R-01) The index copies each scheduled message's send time, so the minute check opens only due messages. An unreadable scheduled message is never sent and told once per run; a series ends only when its message is gone or done, never because a read failed. Rejected: a separate schedule file (a second truth).
- **D-080** Repeating sends at start + k × interval (no drift); missed sends are not made up; the timetable moves on before sending (never two sends); three tries.
- **D-060** A POP3 account keeps its mail in its own folders or in Local Folders (a pseudo-account). Changing storage: copy, verify, save the setting, remove the originals (resumable). A reply goes from the account the mail was addressed to.
- **D-081** Two accounts are the same only with the same incoming user name, host and protocol.
- **D-184** (the owner) An optional **Account name** is shown only inside Chrono Mail (empty: the address; server and protocol added when two would look the same). **Your name** with the address is the From line. Rejected: a "show name or address" choice.
- **D-186** (the owner) A login per server: Outgoing has "Use the same user name and password as for incoming mail" (on by default). No grey help lines in account windows.
- **D-204** (R-05, the owner) Add and Edit account use one set of server boxes; the Port follows Security only while it holds the standard port. **A stored password is never asked for again**: tests and checks take it from the wallet through the engine.
- **D-126** Mail checks have their own pool of 4, so the person's actions never wait behind them. The first check of an imported account reads headers only.

## 6. IMAP (the server is the truth)

- **D-048** An IMAP account is an offline mirror in the same encrypted store; own client (`imaplib` has no caps); one state file per account.
- **D-049** Server to here, per folder: EXAMINE, UIDVALIDITY, removals, flags, new mail; a message enters the state only after it is stored and verified. Removals are refused when more than half of at least 10 vanish. A UIDVALIDITY change matches by Message-ID; unmatched mail goes to `Recovered/<folder>`. Roles from SPECIAL-USE, then the usual names.

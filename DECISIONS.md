# DECISIONS.md

The design rules as they stand now, grouped by topic, kept short so they can be read in full at the start of every session. Every number D-001 to D-227 is here (code and tests cite them); D-030 and D-042 are split over two topics, marked with their part. Measurements, cause chains and the full wording of every decision up to D-161 are in `DECISIONS-ARCHIVE.md`. Search it by number, never read it whole.

**Maintaining this file:** a new decision goes into its topic with the next number (next: **D-228**) and its date: the rule, `Why:` in one line, `Rejected:` only when someone might propose it again. Detail and measurements go in DEVLOG.md. When a decision changes, rewrite its entry to the new state and add "(changed by D-nnn)". Before rewriting an entry, copy its old wording to the end of the archive under its heading with the date. A decision that no longer holds becomes one line: "→ D-nnn".

## 0. The basic rule (read first; it comes before every other decision)

- **D-193** (2026-10-20, the owner) **An account in Chrono Mail is a faithful copy of the account on its server**: mail (IMAP), calendars and tasks (CalDAV), contacts (CardDAV). (1.1) Every action on server data is done on the server first, and here only when the server confirms it. (1.2) Every change on the server (another program, computer, phone, the server itself) shows here at the next synchronisation: new, changed, moved, renamed and deleted, single items and whole folders, calendars and address books. (1.3) Without a connection an action is done here at once, remembered through a restart, and sent when the connection is back; the person never repeats it. (1.4) A lasting refusal of the server (read only, no permission, rejected) that leaves the data different is a sync conflict, settled by the person (Settings > Sync conflicts, R-23/R-24; the design is in REFACTOR.md); a passing failure (no connection, a timeout, 5xx) is tried again. (1.5) Two computers on the same account end up showing the same. (1.6) Exceptions: local data (Local Folders, local calendars, contacts, tasks) is the truth itself; POP3 only downloads and deletes per its leave-on-server setting; data that exists only on this computer only when the owner approved it, case by case (so far: Scheduled messages D-172, the calendar palette D-191; and, given once for all, D-201). Every changelist says how it keeps this rule (server first, offline, server changes shown, refusal); every fix is tested online, offline and back, refused, changed on the server, and with two computers. Nothing counts as obvious: what this rule does not settle is asked. Why: several parts were built differently from what the owner intended (audit round 3, R-23 to R-35).

- **D-201** (2026-10-21, the owner, R-32, R-33) **What the server supports is synced; what it does not support stays on this computer only.** A function the server has itself (IMAP folders, marks, keywords as tags; CalDAV and CardDAV items and their properties) is done on the server and so reaches every other client (D-193). A function the server does not have stays on this computer only: it changes nothing on the server and nothing on other clients, and Chrono Mail puts no extra folders or hidden records on the server to carry it. So far: snooze times, where an archived message came from (Unarchive on another computer sends it to the Inbox), tag colours and shortcuts, tags on a server that keeps no keywords (Kerio), the calendar palette (D-191), Scheduled messages (D-172). This is the case-by-case approval of D-193 (1.6), given once for all: it is not asked per feature. Why: the owner, "one answer that should fit all your questions".

## 3. Storage, index, keys (never lose mail)

- **D-004** Messages are an encrypted Maildir: one file per message, authenticated encryption, random names with the flag suffix (a flag change is an atomic rename). Rejected: SQLite as the store, a container file (PST), zip, mbox.
- **D-005** The index is SQLite, never the truth, rebuildable at any time, and not encrypted (v1).
- **D-006** The model is IMAP-shaped from day one; POP3 is a restricted account on top of it.
- **D-021** Model: five flags (Maildir D F R S T = \Draft \Flagged \Answered \Seen \Deleted). A folder path is a tuple of names. `MessageRef` = (account id, folder path, store id). Unknown Maildir letters are kept (D-024). The model holds no passwords.
- **D-022** `parse_message` never raises: a failure becomes a defect string. Caps in `mime/limits.py`: depth 20, 1,000 parts, header 1 MiB, part 256 MiB, 50 defects. A date without a zone is UTC. The first text/plain and the first text/html are the bodies; the rest are attachments. The original text of the address headers is kept. Non-ASCII addresses are refused (no SMTPUTF8). Fuzz tests: `random`, fixed seed.
- **D-023** AES-256-GCM. Each file has its own key (HKDF-SHA256, 16-byte salt) and a 12-byte nonce. The header (magic CMF1, version, algorithm, 8-byte key id) is the associated data; the key id is derived from the key. The key lives in the OS credential store through `keyring` (service `chrono-mail`, entry `data-key-<id>`). Backup: a recovery file (scrypt N=2^17, r=8, p=1, with caps on what a file may ask) and a 58-character Base32 recovery code. Not built: master password, key change. Rejected: Argon2, a key in a plain file.
- **D-024** Store layout: separator `!` on every platform. Folders are `f-<12 hex>` directories with `folder.json` (path, role); the tree exists only in the paths. A rename rewrites `folder.json` (a subtree deepest first). A delete moves the folder to `.deleted/`; purging is explicit. A message is 32 hex; it is written to `new/<id>`, and a flag change moves it to `cur/<id>!2,<letters>`. Delivery: tmp (exclusive), fsync, rename, fsync the directory, then verify (read back, decrypt, compare); a failed verification removes the copy and raises. Encryption is per account; switching it is not built.
- **D-025** One SQLite index per account, WAL, FTS5 contentless (needs SQLite 3.43 or newer). Body text capped at 100,000 characters. Search terms are prefixes, always quoted (no FTS injection); paging is LIMIT/OFFSET. A rebuild writes a new file and renames it into place. An unreadable message shows as "(damaged message)". `reconcile_index` repairs from directory listings. Rebuild and reconcile live in `sync`, because `index` and `store` are siblings.
- **D-031** Index format history: 2 preview, 3 cleaned preview (D-033), 4 addresses (D-044), 5 sort indexes (D-106), 6 without the partial unread index (D-114), 7 tags (in place, D-128), 8 sender name (in place, D-153), 9 send time of scheduled messages (in place, the engine fills in the Outbox, D-169), 10 the numbers of every folder (in place, counted once, D-208), 11 date is when the mail server received the message (D-226; every older format is rebuilt, the in-place upgrades are gone), 12 sent, the moment the message carries itself (its Date line), with a sort index (the Sent column, D-228; 11 is upgraded in place and its Sent dates filled in while the person works, D-229). Older formats are rebuilt when the account opens. The engine keeps the data key for the session, is safe for concurrent commands, and SQLite waits up to 30 s for another writer.
- **D-229** (2026-10-22, 2.0.281, the owner) **How an index is rebuilt.** At start, before the mail is shown, every place where mail is kept is checked (`index.check`: missing, damaged, too old or too new: rebuild; format 11: upgraded in place, its Sent dates to fill in). The indexes that cannot be used are rebuilt one after the other (`index.prepare`), then the mail is shown, then the Sent dates are filled in (`index.fill-sent`, in batches of 500, from where it stopped). A rebuild counts the messages first (only a listing of the files), so it reports how many of how many (`RebuildStep`, `Engine.rebuilding`). The window (`ui/indexrebuilds.py`): why it happens, "Account 2 of 3: name", a wide bar, "18,000 of 140,567"; the status line "Rebuilding the index of name… 18,000 of 140,567"; the automatic mail checks and the push wait (Refresh still works) and one check follows. **Run in background** only while the old index stays usable (Settings > Rebuild the search index, the filling in); greyed otherwise. **Abort** asks first (Continue rebuilding is the default): with a usable index the rebuild stops and the old index stays; without one the program closes and the rebuild starts again at the next start ("Without a complete index Chrono Mail cannot show the mail of this account"). The mail is never touched: the half-built index is put away. `index.rebuild` keeps the old index in use while the new one is built beside it; it replaces the file only when no command has it open (`IndexGate`: every opened index holds it until closed; Windows refuses to replace an open file), then what came in or changed meanwhile is caught up from the store (`reconcile_index`). Why: the owner; a start with an empty list and only a line at the bottom was confusing, and the Sent column of 2.0.280 needed no full rebuild.
- **D-026** Settings are one JSON file (atomic, owner-only) in the platform config directory; data lives in the platform data directory (platformdirs). Unknown keys are ignored; a damaged file is copied to `.bad` and reported. Account ids are 128-bit hex, validated (they are directory names). The POP3 default policy is KEEP. Passwords are only in the credential store, per account and direction. One data key per installation. `CredentialBackend` is in `core`.
- **D-170** (2026-10-20, 1.1.197, R-20) The key check tells two failures apart and keeps the credential store's own reason: the store answered without the key (`KeyNotFoundError`; the dialog "The encryption key is missing") and the store could not be asked at all, locked or not running yet (`CredentialStoreError`; "The wallet could not be opened": unlock it and Try again). `key.status` carries `problem` and `store_answered`; the dialog shows the reason and Try again shows the newest one. Why: both showed the same guessing text, so the cause of a failed start could not be found (the owner's start on 2026-10-20: Try again worked at once).
- **D-176** (2026-10-20, 1.1.206) **A message has at most two files: the message itself and, only when needed, its properties file.** What the program needs to know of a message beyond the message is kept with the mail, never beside the account that acted. (1) Our own waiting messages carry it in themselves: a repeating message's whole timetable and progress (`X-Chrono-Mail-Repeat`, short text without spaces) plus its next send (`X-Chrono-Mail-Send-At`, which the index copies, so the minute check finds it like any scheduled message). Recording progress replaces the message under the same id (`Store.replace`: written aside, read back, one rename; only for the Scheduled folder, `Mailbox.replace_waiting`). (2) What cannot go into a message, because received mail is kept exactly as it came: one JSON file per message, `properties/<store id>.json` in the mailbox's store (`store/properties.py`): tags, when a snoozed message comes back and to where, where an archived message came from; unknown names are kept. Named after the store id without the marks part, in one folder per mailbox, so a move (one rename of the message) never touches it and a mark change never renames it. Written atomically under a lock per message; a damaged file is copied to `.bad` and fails only that message. Deleted for good: the file goes; a copy gets the tags; a storage move (D-060) takes it along. `tags.json`, `snoozed.json`, `archived.log` and `recurring.json` are gone: taken over once (tags when the store opens; the rest when a mailbox first opens in a run, `engine/old_files.py`, from the mailbox's own folder and those of the accounts that keep their mail in it), each old file removed only after all of it is written, what is already in the new place kept. Why: those files were saved under the account that acted, not where the mail is, so a repeating message from an account in Local Folders was missing from Settings > Scheduled messages and never sent, and Unarchive through Favorites lost the origin (the owner, 2026-10-20). Rejected: one properties file per mailbox (not one file per message, the owner's rule); the properties file next to the message in its folder (a move would be two renames, and a crash between them separates them).
- **D-136** (changed D-026) Every read and save of `config.json` holds one engine lock; changes go through `Engine.change_config` (read fresh, apply, save). Long work happens outside the lock. Rejected: one lock around a whole command.
- **D-220** (2026-10-21, 1.8.263, R-16) **Code two lower layers both need exists once, in the lowest layer both may reach.** The credential store: `core/credentials.py` (`CredentialEntries`: the service name `chrono-mail`, reading, saving and removing an entry, every failure a `CredentialFailure` with its cause and reason, D-127); `crypto/keystore.py` and `config/passwords.py` use it and keep their own error kinds and words (D-170). This thin door to the credential store is the one piece of I/O in `core`. The index files: `index/database.py` (`IndexDatabase`: the SQLite 3.43 check, opening with the 30 s wait, WAL, closed at once when opening fails, "damaged; rebuild it", `BEGIN IMMEDIATE` transactions D-107, the integrity check); `Index` and `PimIndex` (one layer higher, so it may) add their own layout and format check in `_prepare`. The mail servers: `protocols/lineconnection.py` (`LineConnection`: sending, receiving, a line with its cap, exact bytes, the wait of IDLE, every network failure a `ProtocolError`); `ImapClient` and `Pop3Client` keep their connect, STARTTLS and protocol. SMTP uses the standard library and has none of it. Why: two copies drift; a fix in one left the other wrong. Rejected: a new shared layer for three small pieces.
- **D-127** Every failure of the credential store (also D-Bus errors of KDE Wallet) is a normal error with its reason. No automatic retry, because it would hide the fault. The importer goes on without that account.
- **D-035** A missing key at start opens a dialog: recovery code, recovery file, or try again (it says why: D-170). "Not now" leaves a red status line; the menu can restore the key later.
- **D-043** `message.export` writes the .eml as received (atomic, 0600, not encrypted). `message.source` returns at most 2,000,000 characters. `message.text` gives plain text. Printing uses our own escaped markup, never the mail's HTML.
- **D-100** Folders are made under a lock per store (`Store.create_folder`, `ensure_folder`); every code path that makes a missing folder uses `ensure_folder`. `SNOOZED_LOCK` guards the snooze file. `merge_duplicate_folders` repairs twins when the store opens. Not covered: the program and the CLI at the same moment. Cancel snooze: in Snoozed, back to the folder it came from (no record: the Inbox), unread.
- **D-107** Every index change starts with `BEGIN IMMEDIATE`. A missing message file is `MessageNotFoundError`; deleting such a message removes its index line ("deleted").
- **D-108** Maintenance (check, rebuild) runs once per place where mail is kept. Its report can be copied.
- **D-109** A message whose file is gone: delete-type actions (Delete, for good, Trash, Junk) remove it from the index ("gone"); every other action only shows its error. One warning per action. Settings > Security and storage > Repair the search index (`index.reconcile`). The index is never repaired by itself. (1.9.265, R-44: an action on several messages marks a message not done because its file is gone, NotDone.missing, so this warning comes again; it was silent since 1.1.247.)
- **D-115** → D-145.
- **D-145** (changes D-115) The index lock is in `engine/session.py` (`index_lock`). `Engine.open_index` opens an index only inside that lock, also for the automatic rebuild; one rebuild at a time, the others wait.
- **D-125** Bulk import writes a batch without fsyncing each file, then syncs once (`Store.written_together`), and only then writes the journal. A message counts as a duplicate only when its index copy decrypts here. Rejected: writing without any sync.

## 4. Security and privacy

- **D-030** (security part) HTML mail is shown in Qt WebEngine with no JavaScript, plug-ins or storage, off the record. It follows no link and opens no window; only web and mail links are offered, after a question. Every outside request is blocked until allowed for that message. cid pictures are embedded as data. Subjects and headers are never markup.
- **D-215** (2026-10-21, 1.5.257, the owner) **Where a link leads is shown before it is clicked.** While the pointer is on a link in a message (HTML or plain text; the reading pane and the message window), the bar at the bottom of that window shows the link's full address as plain text (never markup; a long one is cut at the right edge); leaving the link, or another message, shows the window's own status text again (it is never changed: `ui/linkhint.py` `StatusLine` shows one or the other). The orange Breeze triangle (`emblem-warning`) comes before the address when the link leads to another **main domain** than the sender's From address: the part someone registers, by the Public Suffix List (`alianz.nl` and `business.alianz.nl` are one, `example.co.uk.evil.com` is `evil.com`), compared in plain letters (IDNA) without regard to capitals (`mime/linkdomain.py`). Web links compare their server, mailto links the address's domain; a bare number address, a server without a main domain and a sender without an address always get it; a link without a domain (a jump, cid:) never. The list is the one built into the package `publicsuffixlist` (MPL-2.0 without the "incompatible" notice, so it combines with AGPL-3.0; pure Python, no other packages), never fetched: hovering contacts nothing. The installers include its `public_suffix_list.dat`. Why: the owner; seeing the real target, and a warning for another domain, protects against links that pretend to be the sender's. Rejected: "the last two parts" as the main domain (wrong for `.co.uk` and many others).
- **D-042** (privacy part) A new-mail notification gives only a count, never a sender or a subject.
- **D-058** → D-082.
- **D-082** When a certificate fails, the person can look at it (`certificate.inspect`: no login) and accept exactly that SHA-256 fingerprint, stored as `host:port=fingerprint`. Only that server skips the chain and name checks, and it refuses every other certificate. A bare fingerprint (from before 0.0.72) applies to all servers of the account. The DAV server counts as its own server. Settings has no list to remove exceptions yet. A certificate the person accepted for an account's mail is also accepted for its calendar server when that shows exactly the same one (changed by D-180). `certificate.inspect` takes kind https for a calendar and contacts server, tls only (1.9.272: the sections' Add account… asked with https and was always refused).
- **D-180** (2026-10-20, 1.1.210, the owner) **Never accept a certificate the person did not accept.** When the calendar server of an account shows exactly a certificate (the same SHA-256 fingerprint) the person already accepted for one of that account's servers, it is accepted for the calendar server too, without asking (`dav.find` returns the pin `host:port=fingerprint`, `dav.link` saves it and refuses a fingerprint the account did not accept). Any other failing certificate: that place is skipped and the result says so. Why: the owner accepted the Kerio certificate for IMAP; a second question for the same certificate is noise, and nobody can show that certificate without the server's key.

## 5. POP3, SMTP, sending

- **D-027** Our own POP3 client (`poplib` refuses lines over 2,048 bytes). Caps: line 1 MiB, message 256 MiB, 1,000,000 messages, timeouts. STLS is never skipped. DELE is committed only by QUIT. Order: retrieve, store and verify, append to the state log with fsync, and only then delete on the server. Policies: KEEP, DELETE_AFTER_DOWNLOAD, DELETE_AFTER_DAYS, DELETE_WHEN_DELETED_LOCALLY (judged from directory listings). Deletion is blocked when the store looks damaged or empty, or when more than half of at least 10 messages are missing.
- **D-036** "Leave all mail on the server" is the default.
- **D-028** SMTP wraps `smtplib` with a capped reply reader (200 lines, 64 KiB). STARTTLS never falls back to plain. Order: build, store a verified Outbox copy, send, move to Sent (Seen). A failure stays in the Outbox and is never resent by itself.
- **D-088** Our Outbox and Sent copies keep Bcc; `without_bcc` strips it just before SMTP. `mail.send-outbox` (Send All). Refresh = Send and Receive All, with a menu (Send and Receive All, Receive All, Send All, per account). Forward as attachment attaches the original unchanged as message/rfc822.
- **D-037** A draft is a message in Drafts (DRAFT + SEEN) with Bcc and `X-Chrono-Mail-Kind`/`-Source`. Saving stores the new version before removing the old. Autosave every 30 s; on close, Save/Discard/Cancel. Outbox messages reopen the same way. The window is finished, and stops autosaving, the moment the engine has the message (scheduled or sent), before any box is shown (1.1.199: an autosave under the confirmation box made a stray draft or "Message not found"). A failed automatic save shows no box: the bottom line of the window says "The draft could not be saved: <reason>" in the theme's red until its next text, and the next autosave tries again; a failed Save asked for also shows the box (1.9.267, the owner: a box every 30 s interrupted the writing).
- **D-055** Send later keeps the message in the Scheduled folder (D-172; before 1.1.200 the Outbox). `mail.send-due` rebuilds it (new Date and Message-ID), stores a verified copy, removes the original, and only then sends.

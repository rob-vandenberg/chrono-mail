# D-316 The index knows which reminders are due
Topics: [[calendars-contacts-tasks]]

(The owner) The calendar index keeps, per event, when its next reminder is due, and the reminder check reads only those events; no limit in days remains. It is a local copy, worked out from the event: the reminders stay in the event (VALARM), so two computers end up the same. A repeating event keeps only its next reminder, and after it fires the next is worked out; a series without an end and a moved occurrence count like any other. Storing an event, from a sync or from here, works its moment out again; a deleted event has none. Existing events get theirs once in an upgrade, safe when interrupted; a rebuild makes it again. Reminders missed while closed keep the rule of D-313: only what has not begun counts.

(The owner) A task's reminder fires the same way, through the same due moment and the same check: minutes before the due time, or at a fixed time. Repeating tasks, changes from a sync, deleted tasks and reminders missed while closed follow the rules above. A finished task fires no reminder; a task opened again counts again. A cancelled task still exists, but is inert: it fires no reminder, and counts again when its status changes back. A task without a due date fires only a reminder at a fixed time. Existing tasks get their moment once in an upgrade, safe when interrupted.

(The owner) A task's reminders work like an appointment's: the same rows, each Notification or Email, a number and a unit (minutes, hours, days, weeks), a close button, and Add notification, at most 5. A row can also be at a set time, with a date and a time; the reminder is stored in the task. Every reminder of a task is shown and kept, also one from another program; a change of one row never removes another. A task without a due date cannot have a relative reminder, only an absolute one: the rows counted from the due date are greyed with a hover text and stay stored, they do nothing, and count again when the task has a due date again; a due date makes them usable at once; set-time rows stay usable.

(The owner) A cancelled event still exists, but is inert, as a declined event and a cancelled task: it fires no reminder, Notification or Email, and counts again when its status changes back. A cancelled date of a series fires none; the rest of the series still fires. Cancel of a whole series also covers a changed date with no status of its own; a date with its own status keeps it (D-317). Existing cancelled events have their moment worked out again in an upgrade, safe when interrupted. In every calendar view a cancelled event is drawn in a fixed grey that replaces its calendar colour, with the hover text "Cancelled" and the calendar's name; its own colour returns when the status changes back. Whether it counts as busy does not change.

How it is built (not the owner's words): for a task "has not begun" reads "is not yet due", and minutes always count from the due time. Storing marks an item "to work out", and the next look does it, because only the look knows the moment of the last look. A first set time starts at the next whole hour. At a set time… is the last choice of a row's unit list; that list stays usable on a greyed row, the way from there to a set time; without a due date Add notification gives a row at a set time. A task that gets a due date again has its minutes stored as counted from the due date (RELATED=END), so other programs ring them at the same time. A cancelled date is known only from the text, so the upgrade works out every event that has a moment, not only the cancelled ones. Each changed date of a series counts by its own status. The grey is the grey of a cancelled task (`task_grey`). Why and what was measured: the details file.
